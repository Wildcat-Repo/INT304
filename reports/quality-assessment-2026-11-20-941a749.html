Executive Summary

employee-form is a course-sized React 19 SPA that captures employees, saves them to localStorage, and now lists them with a details route. All 13 tests pass, and ESLint reports one warning. The main new finding is in the uncommitted details route. Editing a record on /employees/:id writes that record, including its id, into the new-employee draft. Submitting from / then saves a second employee with the same id. Changes since last assessment (2026-11-10, 2719ecf): the overall score dropped from 6.4 to 6.0. The employee list and routing were added, and tests grew from 12 to 13. Four findings are new: the draft pollution, the no-op details submit, the not-found fallback, and the stale README. The unused logo import and the uncommitted README items are resolved. npm high advisories rose from 15 to 21. Seven earlier findings are still open, including no CI and no validation.

All Findings

High (2)

HIGH Editing an employee's details overwrites the new-employee draft and can save a duplicate id
id details-view-pollutes-draft · dimension architecture · src/App.js:23-29 · src/Components/EmployeeForm.js:27 · src/Components/EmployeeForm.js:44-46 · src/App.js:40
EmployeeDetails reuses EmployeeForm, which seeds state from props.employee, including its id. Any keystroke on /employees/:id runs componentDidUpdate and saves that record, id included, to the current_employee key. Returning to / restores the record into the new-employee form, and Submit keeps its id because of employee.id || Date.now(). The result is two employees with the same id, which means duplicate React keys and a details lookup that finds only the first. (Uncommitted change.)
Recommendation: Give the form a mode prop or a separate storage key, so that only the add form persists a draft. Strip id from form state, and always generate a new id in addEmployee (or later, in the API).
HIGH No CI workflow runs tests or lint
id no-ci-pipeline · dimension devops_cicd · .gitea/workflows/ (absent)
No workflow files exist. Tests and ESLint run only by hand. Carried over from 2026-11-10.
Recommendation: Add .gitea/workflows/ci.yml running npm ci, CI=true npm test -- --watchAll=false, and npm run build.

MEDIUM The Submit button in the details view does nothing
id details-submit-noop · dimension architecture · src/App.js:29 · src/Components/EmployeeForm.js:56-61
EmployeeDetails renders <EmployeeForm employee={employee} /> without onSubmit, so Submit is shown but silently ignored. There is no update/edit path.
Recommendation: Either make the details view read-only, or pass an onUpdate handler that replaces the record by id.
MEDIUM An unknown employee URL shows the draft instead of a 'not found' message
id details-not-found-shows-draft · dimension production_readiness · src/App.js:25-29 · src/Components/EmployeeForm.js:27
When find() returns undefined, props.employee || saved falls back to the localStorage draft, so /employees/bogus displays unrelated data.
Recommendation: Render a 'Employee not found' message with a link back to the list when employee is undefined.
MEDIUM Form accepts empty or invalid submissions
id no-form-validation · dimension security · src/Components/EmployeeForm.js:56-61 · src/Components/EmployeeForm.js:68-104
There is no required attribute and no checks in handleSubmit. Empty employees can be saved. This matters more once the data goes to MySQL. Carried over.
Recommendation: Add required to name (and email), validate in handleSubmit, and repeat the validation server-side in the planned API.
MEDIUM Draft stays after submit, so repeat clicks save duplicates
id draft-not-cleared-on-submit · dimension production_readiness · src/Components/EmployeeForm.js:56-61 · README.md:63-65
handleSubmit never resets state or removes current_employee. The README documents this. Carried over.
Recommendation: After a successful onSubmit, reset to defaults and remove current_employee.
